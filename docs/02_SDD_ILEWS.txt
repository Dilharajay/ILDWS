1. INTRODUCTION
---------------

1.1 Purpose
    This System Design Document (SDD) describes the architectural and detailed
    design of the Intelligent Landslide Early Warning System (ILEWS). It
    translates the requirements defined in the SRS into concrete technical
    structures, data flows, module boundaries, and design decisions intended
    to guide the development, integration, and deployment of the system.

1.2 Design Philosophy
    The design of ILEWS is governed by five core principles:

    a. Resilience First: The system must continue to protect lives even under
       degraded conditions (power loss, internet loss, hardware failure).

    b. Edge Intelligence: Critical alert logic must not solely depend on cloud
       connectivity. Edge AI ensures local autonomous operation.

    c. Cost-Effectiveness: All hardware and software choices must permit node
       deployment at under USD $200 per unit to enable dense coverage.

    d. Openness: Where possible, open-source technologies are preferred to
       reduce licensing costs and enable academic reproducibility.

    e. Auditability: Every decision, alert, and data point must be traceable
       and retrievable for post-event forensic analysis.

2.2 Design Rationale for LoRaWAN
    LoRaWAN was selected over alternatives (NB-IoT, Sigfox, WiFi, Zigbee)
    for the following reasons:
    - Range: 2–15 km line-of-sight, sufficient to cover entire slope with
      one gateway.
    - Power: Transmission duty cycle allows years of battery life in mesh.
    - Cost: LoRa modules cost < USD $5 per unit.
    - Independence: Does not require cellular network coverage at node level.
    - Security: AES-128 encryption built into LoRaWAN protocol.

    Oppnet (Opportunistic Networking) is layered on top to allow nodes to
    relay data through neighbours when direct gateway visibility is obstructed
    by terrain or vegetation.


3. LAYER 1: IoT SENSING LAYER DESIGN
--------------------------------------

3.1 Sensor Node Hardware Design

    Central Processor: ESP32-WROOM-32D
    - Dual-core 240 MHz Xtensa LX6
    - 520 KB SRAM, 4 MB Flash
    - Built-in WiFi and Bluetooth (used for local debug/commissioning only)
    - Deep sleep current: ~10 µA

    Sensors and Connections:
    +---------------------------+------------+---------------+
    | Sensor                    | Interface  | Purpose       |
    +---------------------------+------------+---------------+
    | Capacitive Soil Moisture  | ADC (GPIO) | Water content |
    |   (3x per node, 0.5/1/2m)|            | at depth      |
    | Tipping Bucket Rain Gauge | Interrupt  | Surface rain  |
    | MPU6050 (Accel + Gyro)    | I2C        | Ground motion |
    | SCA103T Inclinometer      | I2C        | Creep/tilt    |
    | Piezo Geophone            | Interrupt  | Vibration     |
    | Voltage Monitor (INA219)  | I2C        | Battery level |
    +---------------------------+------------+---------------+

    LoRa Module: RYLR998 or Ra-02 (SX1278)
    - Interface: UART or SPI to ESP32
    - Frequency: 868 MHz (EU) / 915 MHz (Asia/Americas)
    - Tx Power: +20 dBm max, configurable
    - Modulation: LoRa (spreading factor SF7–SF12 adaptive)

    Power System:
    - 20W Mono Solar Panel (weatherproof, UV-resistant)
    - 20,000 mAh LiFePO4 Battery Pack
      (chosen for: high cycle life, thermal stability in equatorial heat,
       no thermal runaway risk unlike Li-Ion)
    - MPPT Charge Controller (12V system)
    - Estimated node autonomy: >7 days without sun

    Enclosure:
    - IP68-rated ABS plastic box
    - Silica gel desiccant packets (replaced at maintenance intervals)
    - Cable glands on all cable entry points
    - UV-stabilised outer coating

3.2 Firmware Architecture

    The ESP32 firmware is structured as follows:

    /firmware
    ├── main.cpp               -- Entry point, task scheduler
    ├── sensors/
    │   ├── soil_moisture.cpp  -- ADC read, calibration curve
    │   ├── rain_gauge.cpp     -- Interrupt counter, volume calc
    │   ├── mpu6050.cpp        -- I2C driver, wake-on-motion
    │   ├── inclinometer.cpp   -- I2C driver, angle calculation
    │   └── geophone.cpp       -- FFT on interrupt burst
    ├── comms/
    │   ├── lora.cpp           -- LoRa packet build and transmit
    │   └── oppnet.cpp         -- Peer relay logic
    ├── power/
    │   └── sleep_manager.cpp  -- Deep sleep scheduling, wake sources
    └── config/
        └── config.h           -- Node ID, thresholds, intervals

    Firmware Operating Cycle (10-minute nominal):
    1. Wake from deep sleep (RTC timer)
    2. Power up sensors (300ms stabilisation)
    3. Read all sensors (200ms)
    4. Validate readings (range checks)
    5. Build JSON packet
    6. Transmit via LoRa (1s Tx window)
    7. Await ACK (2s timeout)
    8. Retry up to 3x if no ACK
    9. Log to EEPROM if 3 failures
    10. Return to deep sleep

    Anomaly Acceleration Mode:
    If any reading exceeds a preconfigured warning threshold, the node
    enters "rapid mode" and samples at 1-minute intervals. This is reset
    after a configurable calm period (e.g., 30 minutes below threshold).

3.3 Data Packet Specification

    Packet Format: JSON over LoRaWAN payload (packed to <51 bytes)
    {
      "id":  "A1",           -- Node ID (4 chars max)
      "ts":  1715623000,     -- Unix timestamp (int32)
      "sm1": 45.2,           -- Soil moisture depth 1 (%)
      "sm2": 52.1,           -- Soil moisture depth 2 (%)
      "sm3": 60.8,           -- Soil moisture depth 3 (%)
      "rn":  0.2,            -- Rainfall (mm since last reading)
      "tx":  0.01,           -- Tilt X (degrees)
      "ty":  0.00,           -- Tilt Y (degrees)
      "ax":  0.02,           -- Acceleration X (m/s²)
      "ay":  0.01,           -- Acceleration Y (m/s²)
      "az":  9.81,           -- Acceleration Z (m/s²)
      "vib": 12.5,           -- Vibration dominant frequency (Hz)
      "bat": 12.4,           -- Battery voltage (V)
      "rssi":-85             -- Signal strength (dBm)
    }


4. LAYER 2: EDGE COMPUTING LAYER DESIGN
-----------------------------------------

4.1 Hardware Platform
    Primary:  Raspberry Pi 4 Model B (4GB RAM)
    Alternate: Nvidia Jetson Nano (for heavier local ML inference)
    LoRa HAT: RAK2245 Pi HAT (LoRaWAN concentrator for Pi)
    4G Modem: Huawei E3372 USB Dongle or Quectel EC25 HAT
    Power:    Same solar + LiFePO4 system as nodes; sized for 72hr backup

4.2 Edge Software Stack

    Operating System: Raspberry Pi OS Lite (64-bit, Debian Bookworm)

    Services:
    +-------------------------------+----------------------------------+
    | Service                       | Technology                       |
    +-------------------------------+----------------------------------+
    | LoRaWAN Network Server        | ChirpStack (open-source)         |
    | Local MQTT Broker             | Eclipse Mosquitto v2.0           |
    | Data Validator & ETL          | Python 3.11 script               |
    | Local Database (buffer)       | SQLite 3                         |
    | Local ML Inference Engine     | TensorFlow Lite or ONNX Runtime  |
    | Cloud Sync Agent              | Python 3.11 + Paho MQTT client   |
    | System Monitor                | Systemd watchdog + cron          |
    | OTA Update Manager            | Ansible pull or custom updater   |
    +-------------------------------+----------------------------------+

4.3 Edge Processing Logic (Python)

    The core edge processing pipeline (gateway_processor.py):

    Step 1: Subscribe to Mosquitto topic `sensors/slope_XX/data`
    Step 2: Deserialise JSON packet
    Step 3: Validate:
            - All required fields present
            - No NaN or None values
            - Values within physical limits (soil moisture 0-100%,
              voltage >9V warning, <7V critical, etc.)
            - Timestamp within 60 seconds of gateway clock
    Step 4: Write to SQLite buffer table `raw_readings`
    Step 5: Check connectivity to cloud MQTT broker
            - If connected: forward packet to cloud, mark as "synced"
            - If not connected: mark as "pending", retry every 60s
    Step 6: Run local inference model on latest 30-min sliding window
    Step 7: If local score >= RED threshold:
            - Activate GPIO siren relay
            - Log alert to local `alerts` table

4.4 Local ML Model
    Model Type: Pre-trained TensorFlow Lite or ONNX model (compressed from
    cloud model; quantised to INT8 for Pi hardware)
    Input Features: Last 30 minutes of sensor readings (sliding window)
    Output: Single risk score (0.0–1.0)
    Update: New model pushed from cloud via OTA when cloud model is retrained

------------------------------------

5.1 GCP Services Used

    +--------------------------------+-----------------------------+

    +--------------------------------+-----------------------------+
    | MQTT Ingestion                 | GCP Pub/Sub + MQTT bridge   |

    | ML Serving                     | TensorFlow Serving (GKE)    |

    | Monitoring                     | Prometheus + Grafana (GKE)  |
    | Alerting Logs                  | GCP Cloud Logging           |
    | SMS                            | Twilio API                  |
    | Push Notifications             | Firebase Cloud Messaging    |

5.2 Kubernetes Service Architecture

    Namespace: ilews-production

    Deployments:
    1. mqtt-broker         -- Cloud MQTT entry point (EMQX or HiveMQ)
    2. etl-processor       -- Consumes Pub/Sub, validates, writes to DB
    3. ml-inference        -- TF Serving container, REST endpoint
    4. fastapi-backend     -- API server, business logic, auth
    5. notification-svc    -- Listens for RED/ORANGE events, dispatches
    6. mlflow-server       -- Model registry, experiment tracking
    7. prometheus          -- Metrics collection
    8. grafana             -- Metrics visualisation

    Scaling Policy:
    - etl-processor: HPA (Horizontal Pod Autoscaler), 2–10 replicas
    - fastapi-backend: HPA, 2–20 replicas based on request rate
    - ml-inference: HPA, 2–5 replicas

5.3 Data Ingestion Flow

    Edge Gateway
        → MQTT publish (TLS) to Cloud MQTT Broker
        → GCP Pub/Sub Topic: `ilews.sensor.raw`
        → ETL Processor Service (Kubernetes pod):
            - Validates schema
            - Deduplicates by (node_id, timestamp)
            - Enriches with slope metadata (lat/lng, slope_id)
            - Writes to TimeScaleDB: table `sensor_readings`
            - Writes recent value to Redis key: `node:{id}:latest`
            - Publishes to internal topic: `ilews.sensor.processed`
        → ML Inference Service:
            - Retrieves sliding window for slope from Redis + DB
            - Runs inference
            - Writes score to `risk_scores` table
            - If score crosses RED/ORANGE threshold:
              publishes to `ilews.alerts` topic
        → Notification Service:
            - Consumes `ilews.alerts`
            - Dispatches SMS (Twilio), push (FCM), dashboard WebSocket event


6. MACHINE LEARNING PIPELINE DESIGN
--------------------------------------

6.1 Model Architecture

    Model Type: LSTM (Long Short-Term Memory) Neural Network
    Rationale: Landslide precursors manifest as temporal patterns over hours
    to days. LSTMs are specifically designed for sequential time-series data
    and can capture long-term dependencies (e.g., sustained rainfall preceding
    failure 6 hours later).

    Input: Time-series window of [T-24h to T] (configurable), resampled to
           15-minute intervals → 96 timesteps
    Features per timestep (per node): sm1, sm2, sm3, rn, tx, ty, ax, ay,
                                      az, vib, bat (11 features)
    Architecture:
      Input Layer → LSTM(128) → Dropout(0.2) → LSTM(64) → Dropout(0.2)
      → Dense(32, ReLU) → Dense(1, Sigmoid)
    Output: Risk probability score (0.0–1.0)

    Alternative: If labelled failure data is scarce, an Autoencoder-based
    anomaly detection approach is used as a complement: the model learns
    "normal" sensor behaviour; high reconstruction error = anomaly = elevated
    risk signal.

6.2 Training Data Requirements
    - Historical sensor readings from all deployed nodes
    - Labelled failure events (where known) with timestamps
    - Synthetic augmentation using slope simulation models
    - Minimum dataset: 12 months of continuous readings before model is
      considered production-ready

6.3 Feature Engineering
    - Rolling statistics: 1h, 6h, 24h moving averages and standard deviations
    - Derived: Cumulative rainfall (antecedent rainfall index)
    - Derived: Rate of tilt change (velocity of deformation)
    - Derived: Soil moisture gradient across depths (infiltration front)
    - Categorical: Time of day, season (monsoon flag)

6.4 EDA Strategy
    - Seasonal Decomposition (STL): Separate daily evaporation cycles from
      monsoon-driven saturation trends.
    - Lag Correlation Analysis: Determine delay between peak rainfall and
      peak soil moisture at each depth.
    - CUSUM / Bayesian Changepoint Detection: Identify shifts in baseline
      tilt or moisture that may indicate creep onset.
    - SWCC Hysteresis Plots: If tensiometer data available, plot soil suction
      vs moisture to characterise soil hydraulic behaviour.

6.5 MLOps Workflow
    Trigger: New labelled event data available OR scheduled monthly retraining
    Steps:
      1. Data pull from TimeScaleDB (feature extraction pipeline)
      2. Feature engineering and normalisation
      3. Train/val/test split (temporal split, NOT random)
      4. Model training (Vertex AI or GKE training job)
      5. Evaluation: AUC-ROC, precision/recall, FAR, lead time validation
      6. If FAR < 5% and lead time > 2hrs: promote to staging
      7. Shadow mode testing (run alongside live model, compare outputs)
      8. Promote to production (blue-green deployment)
      9. Old model archived in MLflow registry
      10. Edge TFLite model updated via OTA


7. DASHBOARD & MAP INTERFACE DESIGN
--------------------------------------

7.1 Technology Stack
    Frontend Framework: React.js (TypeScript)
    Map Library: Leaflet.js with OpenStreetMap tiles (or custom basemap)
    Charting: Recharts or Chart.js
    Real-time: WebSocket (Socket.IO) connection to FastAPI backend
    State Management: Redux Toolkit
    Styling: Tailwind CSS
    Mobile: Progressive Web App (PWA) with offline caching

7.2 Map Interface Design

    The map is the primary operational view. Design principles:

    a. Node markers are placed using manually entered coordinates (lat/lng).
       There is no GPS. Administrators enter coordinates from survey maps,
       physical measurement, or topographic reference.

    b. Each node is represented by a circular marker coloured according to
       current risk level:
         GREEN  (#4CAF50) – Low risk
         YELLOW (#FFEB3B) – Elevated risk
         ORANGE (#FF9800) – High risk
         RED    (#F44336) – Critical / Imminent failure

    c. A translucent risk zone polygon/heatmap is rendered around each node
       to visualise spatial risk spread. The radius of this zone scales with
       the risk score (larger = higher risk).

    d. Clicking a node opens a side panel showing:
       - Node ID and slope name
       - Last update timestamp
       - Current sensor readings (tabular)
       - Risk score gauge
       - 24-hour trend sparklines for key sensors
       - Alert history list

    e. A legend and global risk summary widget appears in the map corner
       showing count of nodes in each risk category.

8. ALERT & NOTIFICATION SUBSYSTEM DESIGN
------------------------------------------

8.1 Architecture

    Risk Score Event (RED/ORANGE)
             ↓
    [Notification Service – Kubernetes Pod]
             ↓
    ┌────────────────────────────────────┐
    │  Alert Record written to DB        │
    │  (alert_id, slope_id, level, ts)   │
    └────────────────────────────────────┘
             ↓
    Dispatcher (parallel channels):
      ├── Twilio REST API → SMS to registered contacts
      ├── FCM API → Push notification to mobile app
      ├── WebSocket event → Dashboard real-time alert
      └── GPIO trigger → Edge gateway activates siren
                         (via MQTT reverse-command)

8.2 SMS Message Template

    [ILEWS ALERT]
    Level: RED – IMMINENT LANDSLIDE RISK
    Slope: {slope_name}
    Node: {node_id}
    Time: {timestamp}
    Score: {risk_score}
    Action: INITIATE EVACUATION. Contact NDMC immediately.
    Map: https://ilews.gov/map?slope={slope_id}

8.3 Retry Policy
    - Failed SMS: Retry 3x at 30-second intervals, then log as FAILED
    - Failed push: Retry 3x at 10-second intervals, then log as FAILED
    - All failures generate a SYSTEM ALERT SMS to System Administrator


9. SECURITY ARCHITECTURE
--------------------------

9.1 Encryption
    - Transport: TLS 1.3 on all HTTPS and MQTT connections
    - LoRaWAN: AES-128 (device and application session keys)
    - Database: AES-256 encryption at rest (GCP managed keys)
    - Sensor node to gateway: LoRaWAN AES-128 (protocol-native)

9.2 Authentication & Authorisation
    - API: OAuth 2.0 bearer tokens (JWT, RS256 signed)
    - Dashboard: Keycloak (open-source Identity Provider) or GCP IAP
    - Role mapping: System Admin, Operator, Analyst, Government Viewer,
      Read-Only Stakeholder
    - Node authentication: LoRaWAN DevEUI/AppKey provisioned at manufacture

9.3 Network Security
    - Edge gateway: Firewall rules permitting only MQTT outbound (port 8883)
    - Cloud: VPC with private subnets; databases not exposed to internet
    - Load balancer: WAF (Web Application Firewall) rules on GCP
    - SSH to edge devices: Key-based only; password auth disabled

9.4 Audit Trail
    - All API calls logged with user ID, timestamp, endpoint, result
    - All alert events logged immutably
    - Logs retained in GCP Cloud Logging for 7 years minimum

11. FAILURE MODES & RESILIENCE DESIGN
----------------------------------------

+----------------------------+-----------------------+------------------------------+
| Failure Mode               | Detection Method      | Mitigation / Response        |
+----------------------------+-----------------------+------------------------------+
| Sensor node power failure  | Missing heartbeat     | Alert admin; redeploy        |
| LoRa comms failure         | No packets > 15 min   | Oppnet relay; alert admin    |
| Edge gateway internet loss | Ping monitor fails    | Edge AI mode; SQLite buffer  |
| Edge gateway power failure | UPS low voltage alert | 72hr battery; solar backup   |
| Cloud DB failure           | Health check fails    | Redis cache serves dashboard |
|                            |                       | GCP Cloud SQL HA failover    |
| ML inference service crash | Kubernetes liveness   | Auto-restart by K8s          |
| Notification failure       | Delivery receipt none | 3x retry; admin alert        |
| Cloud zone outage          | GCP monitoring alert  | Multi-zone GKE deployment    |
+----------------------------+-----------------------+------------------------------+

Edge-Only Survival Mode (Internet Lost):
  The edge gateway transitions to full autonomous mode:
  - Local ML model runs inference on local data
  - Local siren triggers if RED threshold met
  - Dashboard continues to serve last known data (local nginx cache)
  - Data buffered in SQLite; sync resumes on reconnection
  - Battery backup sustains operation for minimum 72 hours
